## Auftrag und Vertrauensgrenzen

Der Nutzer beschreibt Features direkt in ChatGPT und möchte danach möglichst ohne weitere Agentensteuerung bis zur testbaren DEV-Version gelangen. GitHub ist die technische Source of Truth für Aufgaben, Commits, Pull Requests und CI; Cloudflare hostet die statische WebApp. Der Agent entwickelt auf einem Feature-Branch und erstellt einen PR. `main` bleibt geschützt; der Agent merged seinen eigenen PR nicht. Der Nutzer prüft die PR-Vorschau und merged nach den vorgeschriebenen Checks. Ein erfolgreicher `main`-Commit wird danach automatisch auf stabilem DEV bereitgestellt. PROD ist nicht eingerichtet; eine spätere Bereitstellung benötigt eine ausdrückliche menschliche Freigabe.

**Wichtige Grenze:** Der bisherige Feature-Durchlauf beweist den ChatGPT-zu-PR-Preview- und PR-zu-DEV-Pfad. Er beweist noch nicht, dass ein Coding-Worker auch nach Ende einer ChatGPT-Sitzung ohne weitere Steuerung zuverlässig weiterarbeitet. GitHub Actions übernimmt CI und Deployment nach dem Start selbstständig; die Dauerhaftigkeit der Codierphase ist als eigenes Milestone offen.

## Konkreter Einstieg für den nächsten Worker

1. `main`, offene Issues/PRs, das Ruleset, die jüngsten CI-/Deploy-Läufe und [die Aufgabenliste](docs/development/next-steps.md) abrufen. Diese V8 ist eine datierte Momentaufnahme.
2. Einen **kleinen Feature-Wunsch** einmalig direkt in ChatGPT beauftragen lassen und den Durchlauf bis zum PR beobachten, ohne den Coding-Agenten nachzusteuern. Der Auftrag muss so gewählt sein, dass Akzeptanzkriterien ohne Rückfragen aus dem Repository ableitbar sind. Die Prüfung, ob Codierung bei geschlossener ChatGPT-Sitzung tatsächlich weiterläuft, erfordert einen echten unbeaufsichtigten Versuch; Erfolg nicht allein aus vorhandenen CI-Läufen ableiten.
3. Für einen neuen Auftrag ein eigenes Issue nur bei Bedarf automatisch erstellen, von aktuellem `main` einen `agent/<issue>-<slug>`-Branch anlegen, ausschließlich dessen Scope implementieren und relevante Verhaltenstests ergänzen. `pnpm install --frozen-lockfile`, `pnpm check` und bei kritischem UI-Pfad Playwright ausführen. Falls die lokale Umgebung den Next-Build mit `uv_resident_set_memory` blockiert, die Grenze präzise melden und GitHub CI als unabhängige Verifikation abwarten.
4. Genau einen PR mit `Closes #<issue>`, Änderungsbeschreibung, Testergebnissen, Risiken und Konfiguration öffnen. `quality`, `security`, `browser` und den aktuellen PR-Preview-Lauf prüfen. Weder Ruleset noch Tests umgehen. Human Review und Merge abwarten; eigenen PR nicht mergen.
5. Nach menschlichem Merge den neuen `main`-CI-Lauf, den **tatsächlich erfolgreichen** stabilen DEV-Deploy samt Smoke-Test und die Bereinigung der PR-Ressourcen anhand der Runs prüfen. Erst dann die DEV-URL als bereit melden und die Dokumentation mit echten Nachweisen fortschreiben.

**Akzeptanz für das offene Milestone:** Eine einzige Feature-Eingabe startet den Auftrag; der Coding-Teil erreicht ohne weitere manuelle Agentensteuerung einen geprüften PR mit testbarer Vorschau. Nach menschlichem Review/Merge liefern die automatischen GitHub-Workflows den gemergten Commit auf stabilem DEV aus. Wenn der Coding-Teil bei Sitzungsende stehen bleibt, diesen konkreten Ausfall dokumentieren und erst danach eine dauerhafte Worker-Lösung auswählen. Der menschliche Merge ist weiterhin eine bewusste Grenze, keine fehlende Automatisierung.

## Weiter offene Aufgaben in Prioritätsfolge

1. Obigen unbeaufsichtigten Ende-zu-Ende-Versuch durchführen und bei Bedarf einen dauerhaften Coding-Worker entwerfen.
2. PR-Preview-URL und Browserstatus deutlich im PR/Deployment anzeigen; bei mehreren Commits nur den aktuellen geprüften Commit als bereit kennzeichnen.
3. DEV-Rollback-Prozedur dokumentieren und mit anschließendem Smoke-Test erproben.
4. Rechte und Lieferkette der Actions regelmäßig überprüfen: `workflow_run`, Artefakte, Token, Secrets, verwendete Actions-Versionen sowie Dependabot-PRs.
5. PROD erst bei realem Bedarf mit separatem Environment, Freigabe, Promotion-Kriterien und Rollback planen.

Die detaillierten To-dos stehen in [`docs/development/next-steps.md`](docs/development/next-steps.md). Für neue Aufgaben immer eigene Issues/PRs verwenden. Diese Übergabe autorisiert weder einen Ruleset-Bypass noch einen PROD-Deploy.
